## Decisions

1. **Contain existing failure paths before expanding autonomy.** Fix native argv handling, sensitive path authorization, terminal behavior, API compatibility and alternate transition bypasses. Do not add another independent steering guard, fabricate PASS or broaden child tools to meet an impossible contract.
2. **Use one scheduling/control authority as the target architecture.** Existing extensions should propose typed interventions; only accepted transitions may schedule inference. Prefer adapters around Pi sessions and a single-writer controller over another set of independent launchers. Select SDK/RPC transport only after pinned-runtime protocol tests; private print stdout cannot provide peer messaging.
3. **Separate scoped task disposition from verification success.** Completed plan, expected failing test, blocker and cancelled work are legitimate reports. Actual checks attest task/epoch/artifact/producer. Eliminate caller-manufactured authoritative verifier acceptance.
4. **Treat OS isolation as necessary for arbitrary native execution.** Regex checks remain defense in depth, never the primary effect allowlist. Broker policy/credentials and collect logs outside ordinary worker write authority. Unknown shell effects require a scoped grant or restricted execution environment.
5. **Retain supported runtime summarization and a structured checkpoint.** Remove arbitrary oldest-prefix replacement. Durable task state, constraints and references must survive compaction without retaining stale system directives.
6. **Pin ECS 9.2.0 as the proposed implementation schema**, subject to fetching that exact release schema and validating mappings in the implementation stage. Current review fetched official field references; no schema ingestion test has run. Do not label existing logs ECS-compliant. Use standard tracing keyword fields, duration in nanoseconds, success/failure/unknown outcomes, plus `pi.*` for agent/task/epoch/approval/policy/usage. See [Elastic tracing fields](https://www.elastic.co/docs/reference/ecs/ecs-tracing) and [event fields](https://www.elastic.co/docs/reference/ecs/ecs-event). Validate permitted category/type arrays against the pinned artifact rather than inventing agent categories.

## Target state transitions and protocol

States: queued → running → waiting-for-tool/agent/approval/user, reviewing or recovering → succeeded/failed/blocked/cancelled. Only the controller commits transitions and reserves work. Every wait stores owner, reason, deadline and resolution event. Blocked is dormant until an authorized relevant change; cancelled/succeeded/failed invalidate pending messages and process reservations. A clarification revises a task explicitly; unrelated intent creates a new epoch. Task leases carry fencing generation; stale workers can submit observations but cannot publish authoritative completion.

Spawn envelopes carry bounded objective, allowed resources/tools, artifact refs, task completion contract, deadline and reserved budget. Messages carry ID, authenticated actor/recipient, task/epoch, kind, reply-to, TTL and ack state. Duplicate deliveries are idempotent. Read-only control operations (report/help/cancel acknowledgement) do not require filesystem write permission. Parent-child waits are graph-checked; waiters do not consume all runnable slots. Rescue uses one bounded reserve inside mission limits and cannot recursively spawn rescuers or administer policy.

Candidate initial lab policy: four concurrent workers, depth two, eight total spawns, 30 model requests, two recovery interventions, 15-minute task deadline; supervisor at most two requests within that total. These are configurable **lab limits**, not measured production defaults. Persist remaining counts/cost/tokens where reliably observed; unknown usage is unknown and request/time caps still apply. Do not hard-code these numbers as a universal workload policy.
