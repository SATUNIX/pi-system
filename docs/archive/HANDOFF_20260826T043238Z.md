## What Phase 3 actually shipped (ground truth)
- `extensions/conductor/agents/validator.md` is strictly read-only:
  `read, grep, find, ls`, with three independently reported PASS/FAIL
  questions.
- `extensions/conductor/validate/validator.ts` has the intentionally narrow
  `ValidatorBundleInput` type (`evidence`, `requirement` only), deterministic
  `buildValidatorBundle()`, a schema-limited `dispatch_validator` tool, and
  a separate `record_validator_verdict` tool.
- The durable record is
  `.pi/engagement/findings/<findingId>/verdict.json`, retaining evidence,
  requirement, real/matters/inScope notes, overall pass, and timestamp. A
  `validator:<findingId>` flat summary is atomically rolled into
  `.pi/verdicts.json`, so Phase 1's unchanged `verifierBoardBlocked()` blocks
  validator failures. `findingValidated()` fails closed on missing, malformed,
  failing, or stale records.
- Every dispatch and record/refusal is best-effort audited in `.pi/trace.jsonl`.
  The local audit helper follows Phase 2 self-containment rather than importing
  another extension.
- `tests/conductor-validator-smoke.mjs` tests exact bundle text, schema shape,
  withheld narrative, rejected real/in-scope outcomes, staleness, audit
  refusals, and the unchanged board gate. Run it with
  `npm run smoke:conductor-validator`.
- `remote-review` remains an inert stub. Its old review-escalation intent is
  explicitly documented as superseded by Phase 3 local validator dispatch;
  fold/delete remains a later-phase decision.
