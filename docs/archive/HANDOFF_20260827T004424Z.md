## What Phase 4 actually shipped
- `extensions/conductor/index.ts` owns the version-2 engagement record with
  `recursion: { maxDepth, maxDispatches, dispatchesUsed }`. Existing version-1
  records are read as safe defaults and upgraded on their next durable mutation.
- `dispatch_specialist` is the sanctioned isolated child path. It obtains a
  fail-closed engagement lock, reserves a dispatch before spawn, enforces the
  current `PI_KIT_CONDUCTOR_DEPTH` against `maxDepth`, and explicitly supplies
  incremented depth to `pi --mode json -p --no-session`.
- Default cap selection is depth 2 and eight total specialist dispatches. Both
  allowed/refused decisions and post-run results are best-effort trace-audited;
  the durable reservation audit attempt is made inside the same lock immediately
  after the increment.
- While an engagement is active, Conductor blocks the generic `subagent` tool;
  all specialist delegation must use `dispatch_specialist`. Every engagement
  record read-modify-write (start, phase, and reservation) shares its lock.
- Specialist child environments merge `.pi/engagement/` into
  `PI_KIT_PROTECTED_PATHS`, so protected-paths blocks write/edit and its covered
  shell-write forms against the engagement ledger.
- Specialist bash is deliberately excluded in Phase 4. Bash-capable bounded
  specialists are out of scope until a future phase adds tool-firewall
  command-pattern denial for direct `pi`, `codex`, and `claude` binary invocation
  from governed bash calls; do not restore bash before that structural guard.
- The existing UI status API receives `conductor-recursion`, showing depth and
  dispatches used/cap; vendor footer code was not modified.
- `tests/conductor-recursion-smoke.mjs` injects fake runners and proves depth
  and budget refusals happen before child creation, with durable-state and audit
  assertions. `smoke:conductor-recursion` is in `package.json`.
