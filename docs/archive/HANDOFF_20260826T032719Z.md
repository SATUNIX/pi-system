## Phase 2 scope (do this; nothing more)
Build `agent-synth` — a deterministic template→agent assembler — as a library
inside `conductor` (`extensions/conductor/synth/`, per §8's row for it). No
live dispatch of synthesised agents to do real work yet is required beyond
what's needed to prove the assembler works; the emphasis is the assembler
being pure, deterministic, and heavily tested (§9 calls this "the riskiest new
logic").

Required behavior (§8 `agent-synth` row + §9 Phase 2 bullet):
- A pure function (no live model call, no I/O side effects beyond producing a
  string / writing the one file it's asked to write) that takes: a role brief
  (short string), a list of selected skill names, a tool set (list of tool
  names the synthesised agent is allowed), a model tier (`"hot_path"` or
  `"strong"` — reuse `provider-router`'s `hot_path_model`/`strong_model`
  naming convention, see `extensions/provider-router/index.ts`'s
  `RoutingPolicy` type and `readPolicy()` for the existing convention; do not
  invent a third tier), and a scope stanza (short string or structured data
  describing what this agent is authorised to touch). Output: a
  `.pi/agents/<synth-name>.md` string in the same frontmatter+body shape as
  the four existing static role templates — read
  `extensions/orchestrator/agents/implementer.md` (and the other three in that
  directory) for the exact shape to match: YAML frontmatter with `name` and
  `description`, then a body written in second person ("You are a ...").
- **Skill-name validation against the real catalogue, not an assumed index.**
  There is no machine-readable skills index in this repo yet — `kit/skills-
  catalogue.mjs` generates `docs/skills-catalogue.md` directly from each
  `skills/<name>/SKILL.md`'s frontmatter at doc-generation time. `agent-synth`
  must validate every selected skill name against the real `skills/` directory
  (e.g. `fs.existsSync(path.join(cwd_or_repo_root, "skills", name,
  "SKILL.md"))` — confirm the exact repo-root-finding convention other
  extensions use, e.g. how `skill-forge` locates the skills directory, before
  inventing your own) — an unknown skill name must be refused at synthesis
  time (§7 invariant 3: synthesis is deterministic catalogue assembly, never
  free invention).
- **Out-of-scope refusal at synthesis time.** If the requested tool set or
  target implied by the scope stanza would need something a synthesised agent
  should never get (the design doc doesn't fully specify the exact check here
  — this is the "first line of defence" the design doc mentions in §3b,
  understanding that `pentest-governance-domain`'s deterministic gate at
  tool-call time is the real, second, unconditional line of defence per
  invariant §7.1). At minimum: refuse synthesis if the tool set requests a
  tool name `agent-synth` doesn't recognise from a fixed allow-list you define
  (do not accept arbitrary tool-name strings), and refuse if no scope stanza
  is provided at all (empty/missing scope is a refusal, not a default-allow —
  fail closed, same posture as `verifierBoardBlocked`).
- **Golden-file tests** (§9 Phase 2 DoD): for at least 2-3 representative
  inputs (e.g. a read-only recon-shaped agent, a coding implementer-shaped
  agent), assert the exact assembled `.md` output against a committed fixture
  string, so any unintended drift in the template is caught by a diff, not by
  a human re-reading prose each time.
- **New `kit/verify.mjs` check** (§9 Phase 2 DoD, explicit): every synthesised
  agent template `agent-synth` can produce must declare a scope stanza and a
  tool restriction somewhere inspectable in its output (e.g. a recognisable
  marker line/section in the generated Markdown) — add a check in
  `kit/verify.mjs` that would fail if `agent-synth`'s output ever omitted
  either. Model this after the existing hooks-drift/skill-trigger checks
  added in commit `7d6a19e` (see `kit/verify.mjs` for their shape) — a static,
  deterministic check, not a runtime one.
- Conductor may dispatch a synthesised agent via `subagent` (the existing
  vendor package, `agentScope: "both"`) once one is assembled, but building a
  full dispatch-and-collect-evidence loop is NOT required for Phase 2's DoD —
  that overlaps with Phase 3 (independent validation) and is explicitly listed
  as a later phase in §9. If you do wire a minimal dispatch path to
  demonstrate the assembler end-to-end, keep it minimal and say so clearly in
  your own next handoff; do not treat it as this phase's core deliverable.
- Do NOT implement Phase 3 (the causally-independent `validator` role) or
  Phase 4 (bounded recursion/budget caps) — those are separate handoffs.

## Non-negotiable invariants (do not violate any of these — §7 of the proposal)
1. `agent-synth`/`conductor` never enforces scope/ROE and never becomes a
   gate itself. `pentest-governance-domain` remains the sole deterministic
   authority. A synthesised agent's scope stanza is a *told* boundary
   (embedded in its own prompt), never an *enforced* one — enforcement stays
   downstream, unconditionally.
2. `conductor` never returns `{ systemPrompt }` and never injects a system
   prompt directly (this is already true of Phase 1's code — do not add a
   `before_agent_start` handler that returns `systemPrompt`; only write
   `.pi/agents/*.md` files and the existing context-sieve contribution
   pattern). The kit's own self-containment lint in `npm run verify` checks
   this — if it starts failing after your change, you have violated this
   invariant.
3. **Synthesis is deterministic template/catalogue assembly, never a live
   model free-writing agent behaviour or tool grants** (§7.3, and the whole
   point of §3b's "crucial safety property" paragraph). `agent-synth` must be
   implementable and testable with zero model calls. If your design needs an
   LLM call to decide *which* skills/tools to select, that decision belongs
   to whatever calls `agent-synth` (a future `conductor` command/tool, out of
   this phase's strict scope) — `agent-synth` itself just deterministically
   renders the template from already-decided inputs.
4. Least privilege: a synthesised agent's tool set must never be wider than
   what its role brief actually needs — since Phase 2 doesn't yet have a
   real caller deciding this, the enforcement point for this phase is
   `agent-synth`'s own refusal behaviour (see "out-of-scope refusal" above),
   not a caller you haven't built yet.
5. Fail closed: missing scope stanza, unknown skill name, or unrecognised
   tool name must all refuse synthesis, not silently drop/ignore the bad
   input and produce a partial agent.
6. Bounded recursion / budget caps are a Phase 4 concern — not applicable yet,
   but do not write anything in Phase 2 that would make Phase 4's caps harder
   to add later.
7. Everything audited: if `agent-synth` writes a `.pi/agents/<synth>.md` file
   (as opposed to just returning a string for a test to inspect), that write
   should get a `.pi/trace.jsonl` entry via the same `appendTrace`-style
   pattern already in `extensions/conductor/index.ts` (do not import it —
   self-containment — but the shape/convention should match; consider
   whether `agent-synth`'s module can share a small internal helper with
   `index.ts` within the same extension directory, since self-containment
   only forbids importing *other* extensions, not splitting your own
   extension into multiple files under its own directory).
