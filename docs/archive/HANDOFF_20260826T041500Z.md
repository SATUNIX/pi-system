## Phase 3 scope (do this; nothing more)

Build the `validator` role + its dispatch path (§8 `validator` role template
row + §9 Phase 3 bullet + the full worked description in §3c):

- **New role template** `extensions/conductor/agents/validator.md` (read-only,
  matching the frontmatter+body shape of the 4 existing `orchestrator`
  templates — reuse `reviewer.md`'s `tools: read, grep, find, ls, bash`
  restriction, since a validator is at most as privileged as the existing
  reviewer role, arguably less since a validator should almost certainly not
  need `bash` — decide and justify this explicitly in your own implementation
  notes). It answers exactly 3 questions per §3c, and records them:
  1. **Is it real?** (reproducible from the evidence alone — falsifiability)
  2. **Does it matter?** (significance/severity, judged independently)
  3. **Does it match the requirement/stay in scope?**
- **Structural independence, not just requested independence** (§3c's central
  design point): the validator's dispatch must be given **only** the raw
  evidence (request/response, PoC, diff, test output) and the requirement/
  scope stanza it's meant to satisfy — **never** the finder's chain of
  reasoning or self-assessed severity. This must be enforced by construction
  (e.g. the dispatch path builds the validator's prompt from a narrow,
  explicit evidence+requirement bundle type, not by handing over the finder's
  full context/transcript and trusting the validator to ignore parts of it).
- **Verdict recording.** Verdicts land on the `verifier-board` — read exactly
  how `.pi/verdicts.json` is shaped and written today (search for the
  existing writer, likely in `extensions/verifier-board/` — confirm the real
  extension name and file, do not assume) and decide explicitly whether
  Phase 3 writes into that same file/shape, or whether `conductor` needs its
  own separate verdict-adjacent record that `verifierBoardBlocked()` is
  taught to also read. This is the first real design decision of Phase 3 —
  the design doc doesn't fully pin it down, so read the real code first and
  make an explicit, justified choice, documenting it in your own commit
  message and handoff for Phase 4.
- **Fail-closed report/phase gating** (§3c, §7.5): the Conductor may not
  advance an engagement phase, or let a finding into a report, while a
  required validator verdict is missing, failing, or stale — reusing
  `verifierBoardBlocked()`'s existing fail-closed pattern (already proven in
  Phase 1's `/engagement phase` gate). Since there's no "report" surface yet
  in this repo, the DoD below scopes this down to: a validator verdict must
  exist and pass before a finding can be considered validated by whatever
  Phase 3's own command/API surface is — do not invent a full reporting
  pipeline, that's out of scope.
- **Eval fixture proving independence + rejection** (§9 Phase 3 DoD,
  explicit): a fixture proving a fabricated or out-of-scope finding is
  rejected by the validator and cannot be recorded as validated, AND a
  fixture that inspects the actual constructed validator prompt/input to
  assert it structurally never contains the finder's narrative/reasoning —
  this is a stronger claim than "the validator behaved correctly this one
  time," it's an assertion about the shape of the dispatch mechanism itself.
- Do NOT implement Phase 4 (bounded recursion/budget caps) or wire the
  `engagement` profile (Phase 5) — those are separate handoffs.
- Do NOT build a live dispatch of `agent-synth`-produced agents as part of
  this phase unless it's the minimal glue needed to demonstrate the validator
  independently receiving evidence — if you build any dispatch glue, keep it
  minimal and flag it clearly, matching how Phase 2's handoff scoped a
  similar boundary.

## Non-negotiable invariants (do not violate any of these — §7 of the proposal)
1. `conductor`/`validator` never enforces scope/ROE and never becomes a gate
   itself. `pentest-governance-domain` remains the sole deterministic
   authority.
2. `conductor` never returns `{ systemPrompt }` and never injects a system
   prompt directly. The kit's own self-containment lint in `npm run verify`
   checks this.
3. The validator must be read-only. It must never be given tools that let it
   modify evidence, findings, or the repository.
4. Independence must be **structural** (separate context, withheld finder
   reasoning), not merely requested via a prompt instruction telling the
   validator to "be independent" — a model can be told to ignore something
   and still be influenced by it if it's present in context. Do not pass the
   finder's narrative to the validator, full stop.
5. Fail closed: missing/failing/stale validator verdict blocks whatever
   Phase 3's own report/finding-validated surface is — never silently treat
   a missing verdict as a pass.
6. Bounded recursion/budget caps are a Phase 4 concern — not applicable yet.
7. Everything audited: validator dispatch and verdict-recording events should
   get `.pi/trace.jsonl` entries, matching the existing `appendTrace`-style
   pattern (do not import across extensions — self-containment — duplicate
   the small helper locally as both Phase 1 and Phase 2 already do, or factor
   a genuinely shared internal helper file under `extensions/conductor/` if
   that's cleaner now that there would be 3 call sites).
