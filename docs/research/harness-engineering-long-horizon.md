# Harness Engineering for Long-Horizon Coding Agents

## Core judgement

The strongest current evidence points in one direction: for coding agents, the harness is no longer a thin wrapper around the model. It is a first-class system layer that governs execution, tool use, context, memory, verification, recovery, and safety. Recent surveys formalise this directly, arguing that real-world reliability depends heavily on the execution harness rather than on base model quality alone, and proposing explicit harness taxonomies that separate execution environment, tools, context, orchestration, observability, verification, and governance.

For your goal, that is good news. A carefully engineered harness can make a smaller or cheaper model much more competitive than its raw benchmark profile suggests. There is now direct evidence that automated workflow search can let smaller models outperform stronger baselines on some tasks at a fraction of the cost, that minimal scaffolds can score surprisingly well on software benchmarks, and that self-improving harnesses can materially raise held-out performance without changing the base model. At the same time, the best long-horizon benchmarks still show a substantial ceiling: agents do far better on today's narrower issue-resolution benchmarks than on truly extended, multi-file, multi-step software evolution tasks. So "beat frontier defaults" is realistic in bounded, well-instrumented workflows, but not yet as a universal claim across all software engineering tasks.

The practical implication is that you should optimise for **task-shaped superiority**, not abstract model parity. A custom local stack can absolutely beat out-of-the-box Codex or Claude Code on your repos, your languages, your CI rules, your tools, your review criteria, and your failure patterns. The way to do that is not "more prompting". It is: better decomposition, better state, better verifiers, better recovery loops, better observability, and better packaging of reusable expertise into skills and extensions.

## What the leading harnesses actually add

Pi is unusually important for your use case because it is intentionally minimal. Its design principle is to keep the core small and push workflow-specific behaviour into extensions, skills, prompt templates, and packages; it explicitly does **not** ship built-in MCP, subagents, permission popups, plan mode, to-dos, or background bash. That means Pi is not trying to win by bundling every workflow decision up front; it is trying to give you a coding-agent substrate you can bend to your own harness architecture. Pi extensions can register custom tools, intercept and rewrite tool calls, block dangerous actions, add commands, store persistent session entries, customise rendering, and build full terminal UI components. Pi sessions are tree-structured and branchable, with JSONL persistence, branch summaries, and compaction controls, and the SDK gives you programmatic control over session runtimes, print mode, interactive mode, and RPC mode from TypeScript. Pi also supports the open Agent Skills format, can load skills from Claude Code and Codex directories, and can package extensions, skills, prompts, and themes for distribution.

Codex's harness is opinionated around persistent objectives, structured guidance, plugins, hooks, subagents, review boundaries, and cloud delegation. It layers project guidance through `AGENTS.md`, supports open-standard Agent Skills, uses plugins as the installable unit for skills plus MCP plus app integrations, and offers hooks that can block, rewrite, or annotate tool calls during the lifecycle. Its subagents can run in parallel, have distinct models and instructions, and can operate with custom sandbox settings. More interestingly for long-horizon work, Codex adds **Goals**: persistent objectives with completion conditions and constraints that survive across turns, and it supports auto-review, where a separate reviewer agent handles approval requests at the sandbox boundary rather than the main agent simply halting for a human. OpenAI's own harness-engineering write-up also describes an internal loop where the agent reviews its own changes, requests targeted agent reviews, responds to feedback, and continues until reviewer agents are satisfied. That is not just a product feature list; it is a pretty explicit playbook for practical long-horizon work.

Claude Code's harness is strongest where isolation, memory, and deterministic control meet. It supports open-standard skills, bundled skills, plugin packaging, hooks, subagents, MCP, permissions, and sessions through both the product and the Agent SDK. Its skills are progressively disclosed so that the skill body loads only when used, and it extends the skills standard with invocation control, subagent execution, and dynamic context injection via shell-command interpolation. Its hooks go beyond simple shell interceptors: Claude supports command hooks, HTTP hooks, MCP tool hooks, prompt-based hooks, and experimental agent-based hooks that can launch a subagent to verify conditions before a step is allowed to complete. Its subagents are especially relevant to your problem: they run in isolated context windows with their own system prompts, tool permission sets, and model choices, can be spawned in parallel for independent research paths, can be chained for pipelines, and can now spawn nested subagents. Claude also has a dual memory system: `CLAUDE.md` for persistent human-authored rules and auto memory for learned preferences and repository-specific notes. Finally, the `opusplan` model setting formalises a hybrid harness strategy: use a stronger model for plan mode and a cheaper one for execution mode.

Hermes is the most aggressive example of "the harness itself should learn". Hermes positions itself as a self-improving agent with a built-in learning loop that creates skills from experience, improves them during use, nudges itself to persist knowledge, and builds richer user models across sessions. It supports on-demand skills using the open Agent Skills format, subagent delegation with isolated contexts and restricted toolsets, multiple independent profiles with separate config, memory, sessions and skills, and a durable Kanban system where each worker is a full OS process with its own identity rather than an in-process subagent thread. Hermes also separates identity from project procedure through `SOUL.md`, keeps built-in memory plus optional external memory providers, and ships opt-in plugins that operate through lifecycle hooks, including security guidance, observability, and multi-agent Kanban tooling. The distinctive lesson from Hermes is that memory, skills, and multi-agent routing should not be afterthoughts bolted on top of a chat loop; they should be durable system primitives.

Across all four systems, the repeating pattern is clear. The gains are not coming from one magic planner. They come from a stack of additions: persistent project guidance, expandable skills, isolated workers, lifecycle hooks, safety gates, retrieval and memory, background or cloud execution, and post-action verification. The specific product names differ; the harness motifs are converging.

## What the research says about long-horizon performance

Recent benchmark work is useful here because it separates "the model can often patch a bug" from "the system can sustain long-horizon engineering work". SWE-bench established repository-scale issue resolution as a serious challenge, and SWE-bench Verified tightened the benchmark with a human-filtered subset. But the more recent long-horizon benchmarks make the harder point: performance falls sharply when tasks require extended software evolution, broad file touch, or enterprise-style complexity. SWE-EVO reports that tasks span an average of 21 files and hundreds of tests, and that an agent setup that scores roughly 65% on SWE-bench Verified only reaches about 21% on SWE-EVO. SWE-Bench Pro similarly reports that even leading systems remain below 25% pass@1 under a unified scaffold on its harder, enterprise-oriented task set. Terminal-Bench 2.0 makes the same point outside pure GitHub issue repair: it contains 89 realistic terminal tasks, and the benchmark paper reports that frontier agents score below 65% overall.

That gap matters because it tells you where harness engineering is most valuable. On short or medium tasks, a good base model and a simple loop may already get you far. On long-horizon tasks, failure usually comes from workflow mistakes: losing state, chasing the wrong hypothesis too long, wasting context on unimportant logs, failing to verify, executing steps in the wrong order, or not recovering quickly from an unproductive branch. This is exactly why recent research focuses on workflow optimisation as a graph problem, harness engineering as a separate discipline, and verifier-guided or self-improving scaffolds rather than only on better prompting.

Several results are especially relevant to your ambition of getting a local or smaller model to punch above its weight. AFlow reframes workflow design as a search problem over code-represented workflows and reports average gains over prior automated and hand-designed baselines, including cases where a smaller model beats GPT-4o on specific tasks at a small fraction of the inference cost. Self-Harness shows that model-specific harness adaptation can raise held-out performance substantially across several base models without relying on a stronger external agent. Live-SWE-agent goes even further in software engineering specifically: it starts from the ultra-simple mini-SWE-agent scaffold and autonomously evolves its own scaffold during runtime, reporting 75.4% on SWE-bench Verified without test-time scaling and 45.8% on SWE-Bench Pro. Meanwhile, observability-driven harness evolution work reports that the transferable gains tend to come from tools, middleware, and long-term memory, while prompt-only edits transfer poorly.

There is also a cautionary counterpoint that should shape your design. Agentless shows that a simple three-stage pipeline of localisation, repair, and patch validation can outperform more elaborate autonomous agents on some SWE-bench settings at far lower cost. Mini-SWE-agent shows that a very small bash-only scaffold can still score above 74% on SWE-bench Verified. The lesson is not "never build agents". It is that you should only pay for additional orchestration when it buys something concrete. Over-engineering the harness will absolutely damage a smaller local model if the workflow adds indirection without adding information or control.

## A reference architecture for a TypeScript harness

The most robust way to think about your custom TypeScript harness is as six cooperating layers rather than one "agent loop". This framing is directly aligned with recent harness taxonomies and with what the leading products have converged on in practice.

The first layer is the **execution substrate**. Run every substantial task in an isolated workspace, ideally a worktree or a container, with explicit writable roots and explicit network policy. Pi's deliberate lack of built-in sandbox policy means you can own this layer yourself; Codex and OpenHands show the value of OS-enforced or container-enforced separation; Hermes shows that once you introduce true parallel workers, you also need per-task isolation to avoid shell-state and filesystem collisions. For your stack, I would treat "workspace creation, environment replay, checkpoint, rollback" as first-class harness APIs, not as shell scripts hidden behind the model.

The second layer is the **tool surface**. Keep the primitive tools few, typed, and observable: file read, precise edit, shell exec, grep/glob, git/worktree control, structured test runner, browser/UI verifier, and memory/trace operations. Use MCP where it saves bespoke integration effort, especially for documentation, issue trackers, browser automation, and external observability, but prefer a narrow house style for the tool contracts you call most often. MCP is valuable because it standardises discovery of tools and resources and has an official TypeScript SDK, but the practical lesson from Pi, Codex, Claude, and Hermes is that tool count matters less than tool **shape**: fewer reliable tools with strong schemas and good result normalisation are usually better than a huge uncurated toolbox.

The third layer is **context and memory**. I would use a five-part memory design. Keep a portable project-instructions layer in `AGENTS.md` for repo conventions and build rules; mirror into `CLAUDE.md` only where that ecosystem specifically benefits. Add a procedural layer of skills using the open Agent Skills format. Keep session memory as a branchable tree with compaction and branch summaries. Store episodic traces and tool results outside the model context but indexed for retrieval. Finally, store durable facts and preferences in a separate memory store that can be loaded lightly at turn start. This recommendation is a synthesis, but it follows almost exactly from Codex's layered `AGENTS.md`, Claude's `CLAUDE.md` plus auto memory, Pi's branchable sessions and compaction, and Hermes's split between context files, skills, and persistent memory providers.

The fourth layer is **orchestration**. This is where your interest in DAG tasking belongs, but with restraint. Use DAG execution only when subproblems are genuinely independent or mostly independent: multi-area codebase reconnaissance, several competing bug hypotheses, parallel verifier runs, documentation lookup in parallel with local exploration, or multi-worktree implementation of disjoint subtasks. That is consistent with Codex and Claude, both of which recommend parallel subagents for independent exploration, and with workflow research that treats agent systems as computation graphs. For tightly coupled implementation work, stay mostly sequential and instead rely on branch/fork and rollback. My own inference from the evidence is that a good harness should be **DAG-capable, not DAG-obsessed**. Use a graph scheduler as an option, not as the default shape of every task.

The fifth layer is **verification**. Treat verifiers as a stack, not a single test run. Run cheap structural verifiers first: JSON/schema checks, lint, typecheck, focused tests, policy hooks, file-diff guards, and security-pattern scans. Then run stateful or behavioural verifiers: benchmark scripts, browser checks, UI screenshots, performance thresholds, integration tests. Then run critic or reviewer passes: a smaller verifier model, an agent hook, or a separate reviewer agent. This pattern appears everywhere in the current frontier systems and literature: Claude supports agent-based hooks for live verification, Codex supports auto-review via a reviewer agent, OpenHands exposes critic models for iterative refinement, and SWE-PRM shows that inference-time process reward models can materially improve issue resolution by detecting and correcting bad trajectories during execution.

The sixth layer is **observability and self-improvement**. Every turn should emit structured traces: prompt budget, tools used, files touched, branch chosen, verifier outcomes, retry reasons, stop reasons, and final mergeability. This is not operational garnish. Recent harness-improvement work depends on execution traces to mine weakness patterns and propose falsifiable harness edits, while production guidance from OpenAI, LangChain, and Arize all pushes toward trace-driven loops rather than ad hoc intuition. If you only implement one "fancy" feature beyond basic planning and skills, I would make it a rigorous trace store plus an eval harness that can replay representative tasks and score deltas after every harness edit.

## Concrete extensions worth building for Pi or a TypeScript-native agent

The most valuable Pi extension to build first is a **goal and plan manager**. Pi does not ship built-in plan mode or long-lived goals, but it gives you the pieces: session persistence, tree-structured branches, custom commands, extension events, and SDK control. I would add a `/goal` command that writes a durable goal object into session state, plus a `/plan` command that generates or updates a self-contained execution plan. Borrow the idea from Codex Goals and ExecPlans: make the goal explicit about completion conditions and constraints, and make the plan restartable from the file alone. In Pi, that can live as a session entry plus a checked-in markdown artefact.

The second extension should be a **branch-aware task dispatcher**. Pi already has session trees and branch summaries; use that to create lightweight "worker branches" for exploration, implementation, or verification. A parent task can fork three investigative branches, summarise abandoned paths, and then continue on the best branch. This gives you some of the practical benefits of subagents without needing Pi to have native in-process subagents. If you want stronger isolation, pair each branch with a git worktree or container and store the mapping in extension state. This is, in effect, a Pi-native answer to Codex subagents, Claude subagents, and Hermes delegation.

The third extension should be a **verifier board**. When a coding branch claims it is done, your extension should automatically enqueue a fixed verifier sequence: repository rules, targeted tests, typecheck, lint, static security scan, focused review prompt, and optional browser or UI checks. Pi's `tool_call` interception and custom commands are enough to enforce or rewrite parts of this pipeline, while Codex, Claude, OpenHands, and OpenAI's own internal use all show that multi-stage review loops are central to moving from "looks plausible" to "mergeable".

The fourth extension should be a **trace and eval recorder**. Append structured events to SQLite or JSONL for every turn, with a schema that lets you ask questions like: which tools correlate with successful long tasks; where do retries happen; which skills actually reduce token spend; which verifier blocked the most bad merges; which model fails most often on edit localisation; which subdirectory instructions were actually used. Hermes community examples and vendor guidance both point toward local telemetry as the substrate for real improvement, and the harness-evolution papers turn that into a formal methodology.

The fifth extension should be a **skill generator and curator**. Claude, Codex, Pi, and Hermes all converge on skills as the reusable unit of procedural knowledge. Hermes goes furthest by adding a curator that prunes stale skills and consolidates drift; that is worth copying. Every time a task succeeds after a non-trivial sequence of steps, generate a candidate skill draft, stage it for approval, and measure later whether loading that skill improved pass rate, latency, or token cost. In your stack, successful workflows should become code and skills, not remain hidden in old chat transcripts.

The sixth extension should be an **MCP and local-tool bundler** written in TypeScript. Use MCP for the broad ecosystem edge and native process tools for the inner loop. Pi already has an MCP extension ecosystem; Codex and Claude both support MCP; Hermes supports MCP and toolset filtering; and the official TypeScript SDK makes server-side tool development straightforward. A strong practical pattern is to expose stable, high-value local capabilities behind your own MCP servers: semantic code search, repository map retrieval, CI triage, artefact browser, screenshot diffing, eval replay, and issue/PR introspection. That keeps your harness portable across Pi, Codex, Claude Code, and any future client that speaks MCP.

## A practical build strategy for a local model stack

If you want a local-first stack, I would separate the question "which model?" from the question "which harness?". The latest open coding models have become meaningfully more agent-friendly: Qwen3-Coder-Next is explicitly described as an open-weight model designed for coding agents and local development, with staged agentic training on executable tasks, environment interaction, and reinforcement learning; Mistral's Devstral family is explicitly targeted at software engineering agents, and Mistral recommends Devstral Small 2 or Mistral Small 4 for offline local usage, with Devstral Small 1.1 reporting 53.6% on SWE-bench Verified without test-time scaling. Those are strong foundations for a private, local harness.

But model selection should come **after** you define the harness contract. Build the harness so that the model is replaceable. Start with one local coding model and one stronger remote model only for planning or difficult review if you are willing to allow a hybrid mode. Claude's `opusplan` is effectively a productised version of this exact idea. If you insist on fully local operation, keep the same architecture but swap the "planner" and "worker" roles across two local models or two configurations of the same model. The important thing is not the brand; it is that planning, implementation, verification, and summarisation are different jobs, and the harness should be able to route them differently.

In practice, I would target three stages. First, clone the strongest simple baseline you can manage: a mini-SWE-agent-style bash-first loop with your local model, strict verifiers, and trace logging. Second, add only four harness upgrades: explicit goals, branch/worktree forking, progressive skill loading, and layered verification. Third, introduce controlled parallelism through DAG scheduling only where you can prove task independence. This staged path is faithful to the strongest evidence we have: simplicity wins surprisingly often, while the best gains from advanced harnessing come from measured additions tied to actual failure traces, not from maximal complexity on day one.

## Open questions and limitations

A few important uncertainties remain. "Pi coding agent" is much clearer now than it was a year ago because Pi's current public docs explicitly describe its extension, skills, package, session, and SDK model, but Pi's ecosystem is young and some advanced flows that other agents package as built-ins still need to be built as extensions or external tooling. That is a strength for customisation, but it also means more engineering burden lands on you.

Benchmark performance should also be interpreted carefully. SWE-bench, SWE-EVO, SWE-Bench Pro, and Terminal-Bench measure different slices of the problem, often under different scaffolds and budgets, so you should not treat one leaderboard as a universal ranking of harness quality. The strongest conclusion you can safely take is directional: harness quality matters a great deal, simple systems remain competitive, and long-horizon engineering is still much harder than the popular shorter benchmarks imply.

Finally, a local small model plus a great harness can become **locally superior** for your environment without becoming **globally superior** across all tasks. The evidence strongly supports the first claim. It does not yet support the second. The winning strategy is therefore to make your harness ruthlessly specialised, observable, and self-improving around the work you actually care about. That is where a customised Pi- or TypeScript-based stack has the best shot at beating frontier defaults in practice.
